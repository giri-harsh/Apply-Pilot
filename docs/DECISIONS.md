## Phases 1-3 (as built)
- Pinned TypeScript 6.0.x. | typescript-eslint rejects TS 7.0 (native port); 6.x passes typecheck, lint and build. | Dropping lint.
- Identifiers like `q_17`/`f3`/`x4` are not used as label evidence; trailing digits are stripped and names under 3 chars ignored. | Generated names add noise and false conflicts. | Using raw name attributes.
- Evidence from nearby text alone gets confidence 0.6 (< 0.8 fill threshold), so such fields stay unresolved. | SPEC 17.2: low-confidence interpretation is left unresolved. Phase 4 (AI) is the intended path for these. | Filling on nearby text.
- A "Start date" label is not an alias for availability. | It is equally an education/employment start date; guessing would be wrong. | Aliasing it.
- Fields with the same semantic type, label and section are ambiguous and skipped; "Confirm email" style labels differ and are filled. | Cannot know which duplicate is meant. | Fill the first.
- Fields inside Reference/Emergency/etc. sections are `third_party_contact` and never filled. | They are not the applicant's data. | Fill by label alone.
- Hidden (display:none / off-screen) controls are never touched and not counted in totals. | Honeypots; user cannot see them. | Filling them.
- Existing non-empty values are never overwritten (reported unresolved, or already_correct when equal). | Avoid destroying user input. | Overwrite.
- Report definitions: filled = executed without error; verified = re-read value matches and no validation message; failed = planned but not verified. | Honest counts (SPEC 18.4). | Counting attempts as success.
- Resumed runs re-observe, so a resumed run's report shows earlier fills as `alreadyCorrect`. | SPEC 15.3 forbids replay. | Persisting per-action logs (later phase).
- e2e uses `channel: "chromium"` with headless true; works here (new headless supports extensions). | Brief failure case 7. | headed mode.
- Service worker termination in e2e is done through DevTools (`ServiceWorker.stopWorker`) rather than `chrome.runtime.reload()`. | Reload killed the Playwright context. | Reload.
- Phase 3 tests found and fixed: cancelled runs still sent one more page request (now every page call re-checks run state).

## Phase 4 (universal field understanding)
- AI lives in `src/ai/` (config, errors, types, json, http, gemini, groq, router, storage, classify/*) and is reached only through `AiService` in the service worker. | Module boundary; keys never leave the SW. | Calling providers from the content script.
- Default models: Gemini `gemini-3.5-flash-lite`, Groq `openai/gpt-oss-20b` (json_schema best effort). | Read from the providers' public docs on 2026-10-21 via a summarising fetch tool, not verified against the live APIs. | Older 2.x / llama IDs. **Needs user: verify model IDs** (`pnpm test:live` or "Test connection").
- Plain `fetch` with AbortController, no SDKs; Gemini key in `x-goog-api-key` header, never in the URL. | SW bundle size, key hygiene. | SDKs.
- Hand-written JSON schemas next to the Zod ones (+ a test that they agree on fixtures) and a `toGeminiSchema` converter (inlines `$ref`, drops unsupported keywords, upper-cases types). | zod-to-json-schema adds a dependency and version risk (brief failure case 2). | zod-to-json-schema.
- Provider-level validation only checks the envelope `{mappings: unknown[]}`; each item is validated one by one. | One malformed or malicious item must not discard the good ones. | Strict whole-response schema.
- `profileKey` has an explicit `"none"` value instead of null. | Every provider can express an enum; avoids nullable-schema differences. | Nullable.
- Fallback only on `rate_limit`/`quota` (once). Transient `timeout`/`network`/`invalid_response` get one bounded retry on the same provider. `auth` never falls back. Per-run request budget (3) in config. | SPEC 13.5, no loops. | Retry on everything.
- Gate before AI: only unknown / low-confidence / conflicting fields that are not sensitive, consent, third-party, upload, open-ended, hidden, disabled, populated or custom widgets are candidates. Validator and mapper re-apply the policy after the AI. | SPEC 17.2 risk policy wins. | Trusting the model.
- New sensitive type `government_id` (SSN, passport, Aadhaar, PAN, tax id, driver's licence...). | Found while designing the adversarial AI test: such labels were "unknown" and would have gone to the AI. | Leaving them unknown.
- `MAPPING_FIELDS -> FILLING` was removed; every run goes `MAPPING_FIELDS -> PLANNING -> FILLING`. The Phase 1 state-machine and run-manager expectations were changed explicitly for this. | AI mappings are turned into actions in PLANNING (SPEC 11.8). | Keeping both edges.
- Negative results (model said unknown / proposed a disallowed type) are cached; low-confidence and review-requested ones are not. | Avoid paying twice for the same field; confidence outcomes may change with threshold. | Caching only positives (found by the e2e cache test: sensitive-answer fields were re-requested on every visit).
- E2E mocks HTTP with `context.route` on the two API origins. It does intercept the extension service worker's fetches, so no mock provider exists in any build. A test greps `dist/` to confirm. | Highest fidelity (real provider code runs); brief asked to try route first. | Build-flag mock provider.
- Popup sends `GET_RUN` every 1.5 s while a run is working. | A service worker terminated mid-run is only restarted by an event; the heartbeat wakes it so it rehydrates (found by the kill-mid-AI-call test). If the popup is closed the run resumes on the next wake (popup open, tab event). Documented limitation. | `alarms` permission.
- Custom widgets: inputs with `role=combobox` / `aria-autocomplete` / `aria-haspopup` get `widget: "combobox"` and are left unresolved ("needs a selection"). | Found by the autocomplete portal: typing into an autocomplete was being reported as verified although the page held no selection (SPEC 12.4). Phase 4b implements selection. | Leaving the false success.
- Cross-section duplicates: the same type + label in several sections is filled only in the single clearly personal section (heading matches personal/applicant/contact...), otherwise ambiguous. | "Name" under Previous School must not get the applicant's name. | First occurrence wins.
- Label text "...in this country" matched the `country` alias for a Yes/No select; the select is understood-but-unfillable (no option matches) and never sent to AI. Test label reworded rather than weakening the alias. | The executor refuses non-matching options, so the mis-classification is harmless. | Context-aware alias.

## Phase 5 (job description intelligence)
- Extraction runs in the content script (`src/job/extract.ts`) and is deterministic: JSON-LD JobPosting -> visible h1 / selectors / `<title>` patterns / og tags -> main-content scoring (text length x (1 - link density) + JD-keyword bonus, tightened to the smallest container holding ~all of it). | SPEC 8.1; no AI needed. | Readability-style library (extra dependency, less control over noise rules).
- Visible text only: `hidden`, `aria-hidden`, `display:none`, `visibility:hidden` and the closed part of `<details>` are skipped; buttons, inputs and scripts are never text. | Tabs/accordions requirement; avoids hidden-text injection. | `textContent`.
- Noise exclusion: nav/aside/dialog/forms with inputs, site-level header/footer, ARIA landmark roles, id/class tokens (cookie, consent, sidebar, related, ad-slot...), and any block introduced by a "Similar/Related jobs" style heading. A token whitelist keeps "job-description"/"posting"/"content" containers. | Decoy exclusion. | Hard-coded selectors per site.
- JSON-LD is trusted only if consistent with the visible h1 (token overlap >= 0.5, else the heading wins with a warning); multiple JobPosting blocks pick the one matching the heading; malformed JSON-LD is repaired once (trailing commas/comments) or ignored with a warning; double-encoded HTML descriptions are decoded. | Brief failure case 9; JSON-LD can be stale or wrong.
- Unknown scalars are `null`, lists empty; every guess is recorded in `extractionWarnings` (e.g. "Company inferred from the page title") and lowers `sourceConfidence`. | SPEC 8.2.
- Skills: local dictionary (~150 entries) with synonyms; short caps tokens (ML, NLP, SQL, AWS...) are case-sensitive; ambiguous words (React, Swift, Express, Spring, Go, R...) need capitalisation and/or a skills-list context. Required vs preferred comes from section headings; without headings skills are keywords only (with a warning). | Precision over recall; AI enrichment is the recall path.
- Optional AI enrichment is off by default, behind its own switch, cached by posting hash, and every proposed skill must appear verbatim in the posting. | Cannot invent requirements. | Trusting the model.
- Ranking (`src/job/rank.ts`): documented weights (required 0.35, preferred 0.10, best project 0.20, best experience 0.10, education 0.10, role alignment 0.15), unknown components are dropped and the rest renormalised, every component carries a note, per-project/experience evidence lists "Uses X (required)". Skills count only if the profile records them (skills list, project/experience technologies, or skills named in the user's own descriptions). Education: "Bachelor's or Master's" is satisfied by the lowest listed level or higher. Eligibility language is listed for the user, never scored or answered. | SPEC 8.3 transparency.
- Job context is cached per normalised URL (tracking params and hash dropped) for 6 h in its own storage key; failed extractions are not cached; a cache hit makes no page request. | SPEC 21.1.
- `EXTRACTING_JOB` sits between OBSERVING and DISCOVERING_FORM; the direct edge was removed and the state-machine tests updated. A job on a page with no form is still recorded on the (BLOCKED) run. | The popup must show company/role for job pages that link to a separate form.
- Popup sends `PREVIEW_JOB` on open (read-only; injects the content script under the activeTab grant from the toolbar click). | Real company/role before the user clicks Quick Apply.
- Test infrastructure note: backslashes in shell heredocs / `node -e` snippets were silently halved in this environment, which corrupted regex literals twice (caught by tests/lint). Source edits that contain regexes are now made with the Edit tool. | Process.

## Phase 4b (custom dropdowns and autocomplete)
- Two new `AgentAction` variants, both executable: `select_custom_option {fieldId, optionLabel}` and `fill_autocomplete {fieldId, query, optionLabel}`. | A real use case (SPEC 12.3/12.4) that `fill_text`/`select_option` cannot satisfy: typing is not a selection. Each is validated independently (control kind, widget, option existence when the list is already in the DOM, no empty query, trigger not a submit control). | Overloading `select_option`.
- New control kind `combobox` for non-input triggers (`role=combobox`, `aria-haspopup=listbox`); inputs with `role=combobox` / `aria-autocomplete` stay `text` with `widget: "combobox"`. Triggers inside nav/footer are ignored. | Avoid treating site menus as form fields.
- Interaction: open with a full pointer/mouse/click sequence (many widgets select on mousedown), wait (bounded, polling) for the real options, match the profile value to an option label **exactly** (case-insensitive, normalised), click it, wait for the list to close. On any failure the list is closed again and, for autocomplete, the typed text is restored: no "typed but not selected" residue. | SPEC 12.3/12.4/17.
- Option lists are associated by `aria-controls`/`aria-owns`, else a listbox in the next two siblings; the "single visible listbox" fallback applies only while open and never to a list another trigger claims. | Found by the portal: a dropdown without aria-controls was borrowing the country list.
- Verification reads the displayed selection (not a hidden input), requires the list closed, and for autocompletes blurs the field and waits 350 ms for blur-time validation ("choose one of the suggestions"). The validation-message sibling scan now looks at up to 3 following siblings but stops at the next control. | SPEC 18.1; avoids attributing the next field's error.
- Safety: a trigger that is a `<button>` without `type="button"` inside a form, a submit/reset input, or text that says submit/finalize/certify/apply is never clicked. | "Never click submit" hard rule.
- Custom widgets may now be AI candidates (they can be filled). | Previously excluded because typing could not select.
- The Phase 4 limitation tests for custom dropdowns / autocomplete (expecting untouched fields) were replaced by the 4b behaviour tests in `widgets.spec.ts`. | Explicit, planned change.

## Session 3: live verification, Phase 6, Phase 9 (reordered)
- Phase 9 (recovery and multi-step) is done before Phases 7 and 8. | The single-observation-pass limit blocks real portals; Phase 7 (resume rendering and page-count validation) likely needs the local companion, so it moves to the next session. Phase 8 (adapters) stays evidence-driven. | Keeping the numeric order.
- Live verification (10 real calls, the whole budget): Groq `openai/gpt-oss-20b` with `json_schema` passed. Gemini `responseSchema` returned HTTP 400 ("invalid argument", no field named); `gemini-3.5-flash-lite` with the schema written into the prompt (`geminiSchemaMode: "prompt_only"`) was accepted but timed out at 20 s; `gemini-2.5-flash-lite` is listed by the models endpoint but returns 404 for this key. | Defaults: Groq is now the first provider; Gemini stays `gemini-3.5-flash-lite` in `prompt_only` mode with a 45 s timeout, **unverified**. The mode is a config capability flag (`prompt_only` / `response_json_schema` / `response_schema`), not runtime probing.
- Live calls are counted by the live suite and never log URLs, headers, bodies or keys. The live suite accepts `LIVE_ONLY=gemini|groq` and forwards extra vitest args.
- State-machine test corrected: `OBSERVING -> DISCOVERING_FORM` was listed as invalid because job extraction used to always sit between them. Multi-pass runs and later steps skip extraction (it happens only on the first observation), so the edge is intentional. It moved to the allowed list with the other new Phase 9 edges (`VERIFYING -> ADVANCING_STEP | OBSERVING`, `ADVANCING_STEP -> OBSERVING | READY_FOR_REVIEW`, `DISCOVERING_FORM -> OBSERVING`); the invalid-transition cases remain. | The old test was out of date, not weakened.
- Run-manager unit fakes are now a stateful `FakePage` (fills change the next observation; fields can be revealed by fills, steps change on navigate, fields can be disabled, validation can fail then clear). No timeout was raised.
- Phase 9 harness: the run is one loop of steps; each step is up to 4 passes of observe -> map -> plan -> fill -> verify -> settle, then form-level verification, then control classification and one guarded click. Every limit (SPEC 21.2) is a named constant in `limits.ts`; hitting one ends the run BLOCKED, never FAILED, and keeps the real report. | Passes were needed for fields revealed by earlier fills; the pass cap and the "nothing left to do" exit are what stop dynamic pages from looping.
- Recovery order for a failed field: default strategy, default strategy on a fresh observation, keyboard strategy, then give up with the last reason. A page change under a plan (`replan`) does not count as a failure. | SPEC 11.7 asks for a different strategy per retry; there are only two strategies in the executor today (programmatic and keyboard), so the first two tries differ only by observation.
- The AI is asked about a field at most once per step, and answers it has already given are re-used for recovery. | Re-asking on every pass spent the per-run request budget and made rejected answers retry forever (found by the Phase 6 e2e tests after the multi-pass change).
- A field that holds the profile value but is flagged invalid by the page is not "already correct" (`FormField.invalid`); it goes through recovery. | Otherwise the second pass reported a validation error as success.
- `ai.spec.ts` "dynamic conditional fields" was changed, not weakened: it asserted the Phase 4 limitation that a field revealed by our own fill is left empty "until Phase 9". It now asserts the field is filled and that the unrelated hidden field stays untouched.
- An unreadable cross-origin frame ends the run PARTIALLY_COMPLETED with a note, not BLOCKED: the readable part of the page was still filled and verified, and the frame's required fields cannot be seen. | Blocking would discard real work; the note and the state both say the frame needs the user.
- A "Proceed to payment" button is final even though "proceed" is next-step wording. | Payment and checkout wording always wins over progression wording.
- Disabled-at-observation fields with a recognised type are re-checked twice at 1 s intervals before being reported. | Pages commonly enable a field a moment after an earlier answer or a script; the cost is bounded (2 s per step).
- Playwright `outputDir` moved to `test-results/playwright` because it emptied `test-results/live-results.txt` on every run (the first Phase 6 smoke output was lost this way).
- `autofill.spec.ts` "request monitor ... really observes traffic" was flaky (about one full run in three): it asserted that the page's resource-timing entry count grew by exactly one, and the browser sometimes adds an unrelated entry. It now compares entry names (ignoring the favicon) and asserts the single new entry is the fetched page. The assertion about what was observed is unchanged in strength. | An incorrect, timing-dependent test, not a product bug.

## Phase 7 (resume tailoring, multi-agent build)
- Phase 7 runs in-extension with our own deterministic PDF layout (pdf-lib, an embedded OFL font, text measured with the font itself so the engine knows the exact page count); the Phase 10 companion stays deferred. Cross-origin navigation uses a per-origin optional permission requested from a user click (phase 9b). Gemini stays `prompt_only`.
- Where work runs: the service worker orchestrates and makes every AI call (keys never leave it). Heavy PDF work (layout, validation with pdfjs, import parsing) runs in extension pages / an offscreen document, which reach the service worker only for the `shorten` callback. Binaries are in IndexedDB; metadata is in separate `chrome.storage.local` namespaces.
- A master resume is a set of facts with stable `factId`s and provenance. Variants are rules over factIds. Every tailored line cites `sourceFactIds` (schema-enforced, min 1). The master hash is recorded in each output and checked around every run.
- Upload bytes reach the content script only as base64 chunks over the extension message channel, one transfer bound to one field; there is no page-fetchable URL.
- `FormField.accept` was added so uploads respect the input's `accept` attribute.
- foundation.spec production-manifest test updated for the 'offscreen' permission (Phase 7); not weakened: the exact permission list is still asserted.
- Merge order: B1, B2, B4, then B3 (B3 finished last; it only touches its own paths, so the order changed nothing). No builder edited files outside its ownership except the one appended entry each in docs/agents/CONTRACT_REQUESTS.md that the brief asks for. B1's `shims.d.ts` declared the pdfjs legacy build and shadowed pdfjs' own types, which broke B2; the lead removed that declaration.
- A fontkit import that works in Node/Vitest (`import * as`) is `undefined`-shaped in a Vite browser bundle (the default export is on `.default`): `render.ts` resolves both. Found only by the real-extension e2e (the unit tests ran in Node).
- A resume whose validation fails is kept in the history (so the user can see why) but is never uploaded; an over-limit resume is uploaded only with the explicit overflow warning. "Prepared" and "uploaded" are separate facts on the run record (`resume.uploadVerified`).
- After a verified upload the harness observes, maps and verifies once more, because portals that parse a resume may rewrite fields.
- `longMaster()` fits one page after the fit loop drops low-relevance lines (the loop never drops protected lines, section titles, the most relevant education entry or the last entry of a section). True overflow therefore needs protected lines; it is covered by `resume-integration.test.ts` (all lines protected) and the layout unit tests, not by an e2e fixture.
- Prompt-injection stance for resumes: text from the master and the job is delimited data; the validator rules (numbers, tools, organisations, employment vs project, production claims, certifications, links, keyword stuffing, role inflation, unsupported outcomes, unsupported names, length) decide what may reach the PDF, never the model's own claims.
