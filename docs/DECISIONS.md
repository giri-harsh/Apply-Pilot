## Phase 0
- Repo was empty (only docs/SPEC.md); nothing kept, replaced or removed. | Nothing to audit. | n/a
- Spec complete (sections 1-30 present; numbering matches the brief: 6.2, 9.2, 9.4, 11.5, 11.8, 25.2, 26, 27, 29.7). | Verified by reading the whole file. | n/a
- pnpm installed with `npm i -g pnpm` (v12.14). | `corepack enable` fails with EPERM writing to C:\Program Files\nodejs (needs admin). | corepack prepare (activates but no shim on PATH), npm only.
- Single package with `src/` modules (shared, background, content, popup, options). | SPEC 27 allows a simple single-package layout with clear boundaries; brief forbids monorepo/placeholders. | pnpm workspace.
- Plain multi-entry Vite builds driven by `scripts/build.mjs` (pages build + one IIFE lib build each for service worker and content script) with a generated manifest. | Guarantees single-file content script / SW with no chunk imports (brief failure case 6), avoids CRXJS/Vite version coupling. | CRXJS plugin.
- zod 3.25.x (v3 API, `import "zod"`). | Brief asks to pick one major and pin it; v3 API is the one in the SPEC-era samples. | zod 4.
- TypeScript 7.0.2 / Vite 8 / Vitest 5 / ESLint 10 as installed by `pnpm add`. | Current majors; typecheck and build pass. | Downgrading.
- Content script is injected on demand with `chrome.scripting.executeScript` under `activeTab`; no static `content_scripts`, no `host_permissions` in the production manifest. | Least privilege (SPEC 20.1); one-click flow still works because the toolbar click grants activeTab. | `<all_urls>` content script.
- A separate e2e manifest (`pnpm build:e2e` -> `dist-e2e`) adds only `http://127.0.0.1/*`. | Playwright cannot click the toolbar icon to get an activeTab grant; loopback-only access is the narrowest way to test the real built bundle. Production `dist` has no host permission. | `file://` access, `<all_urls>`.
- Popup accepts `?targetTabId=` to point at another tab. | Lets tests open popup.html in its own tab and still drive a specific page tab; message validation and sender checks are unchanged. | Fake toolbar click.
- Run state stored in chrome.storage.local keyed by tab id (latest run per tab). | SPEC 15.3 persistence; one active run per tab is the duplicate-run guard. On wake, in-flight runs go back to OBSERVING and re-observe (never replay). | storage.session (lost on browser restart).
- Profile provenance: personal facts carry a per-key provenance map (validation fails if a non-empty fact lacks one); every other record carries one provenance object. | SPEC 6.2 without turning every string into a wrapper object. | Wrapper `{value, provenance}` for each field.
- "Current employer/title" only comes from an experience record explicitly flagged `current`; never inferred from a missing end date. | SPEC 6.2 (never silently infer). | Inference.
- Phase 3 never fills: sensitive/eligibility (visa, sponsorship, work authorization, disability, veteran, race, gender, criminal history, salary, DOB, age, relocation), consent checkboxes, third-party (reference/emergency) sections, files, password fields, hidden fields. | Brief hard rules + SPEC 14.5/17.2. | Fill preference values.
- Commits are made at verification points per phase; source for later phases was authored while Phase 1 was being built, so a phase commit can contain code whose own tests land in the next verified step. PROGRESS.md states what was verified. | Practical sequencing. | n/a

## Phases 1-3 (as built)
- Pinned TypeScript 6.0.x. | typescript-eslint rejects TS 7.0 (native port); 6.x passes typecheck, lint and build. | Dropping lint.
- Identifiers like `q_17`/`f3`/`x4` are not used as label evidence; trailing digits are stripped and names under 3 chars ignored. | Generated names add noise and false conflicts. | Using raw name attributes.
- Evidence from nearby text alone gets confidence 0.6 (< 0.8 fill threshold), so such fields stay unresolved. | SPEC 17.2: low-confidence interpretation is left unresolved. Phase 4 (AI) is the intended path for these. | Filling on nearby text.
- A "Start date" label is not an alias for availability. | It is equally an education/employment start date; guessing would be wrong. | Aliasing it.
- Fields with the same semantic type, label and section are ambiguous and skipped; "Confirm email" style labels differ and are filled. | Cannot know which duplicate is meant. | Fill the first.
- Fields inside Reference/Emergency/etc. sections are `third_party_contact` and never filled. | They are not the applicant's data. | Fill by label alone.
- Hidden (display:none / off-screen) controls are never touched and not counted in totals. | Honeypots; user cannot see them. | Filling them.
- Existing non-empty values are never overwritten (reported unresolved, or already_correct when equal). | Avoid destroying user input. | Overwrite.
- Report definitions: filled = executed without error; verified = re-read value matches and no validation message; failed = planned but not verified. | Honest counts (SPEC 18.4). | Counting attempts as success.
- Resumed runs re-observe, so a resumed run's report shows earlier fills as `alreadyCorrect`. | SPEC 15.3 forbids replay. | Persisting per-action logs (later phase).
- e2e uses `channel: "chromium"` with headless true; works here (new headless supports extensions). | Brief failure case 7. | headed mode.
- Service worker termination in e2e is done through DevTools (`ServiceWorker.stopWorker`) rather than `chrome.runtime.reload()`. | Reload killed the Playwright context. | Reload.
- Phase 3 tests found and fixed: cancelled runs still sent one more page request (now every page call re-checks run state).

## Phase 4 (universal field understanding)
- AI lives in `src/ai/` (config, errors, types, json, http, gemini, groq, router, storage, classify/*) and is reached only through `AiService` in the service worker. | Module boundary; keys never leave the SW. | Calling providers from the content script.
- Default models: Gemini `gemini-3.5-flash-lite`, Groq `openai/gpt-oss-20b` (json_schema best effort). | Read from the providers' public docs on 2026-10-21 via a summarising fetch tool, not verified against the live APIs. | Older 2.x / llama IDs. **Needs user: verify model IDs** (`pnpm test:live` or "Test connection").
- Plain `fetch` with AbortController, no SDKs; Gemini key in `x-goog-api-key` header, never in the URL. | SW bundle size, key hygiene. | SDKs.
- Hand-written JSON schemas next to the Zod ones (+ a test that they agree on fixtures) and a `toGeminiSchema` converter (inlines `$ref`, drops unsupported keywords, upper-cases types). | zod-to-json-schema adds a dependency and version risk (brief failure case 2). | zod-to-json-schema.
- Provider-level validation only checks the envelope `{mappings: unknown[]}`; each item is validated one by one. | One malformed or malicious item must not discard the good ones. | Strict whole-response schema.
- `profileKey` has an explicit `"none"` value instead of null. | Every provider can express an enum; avoids nullable-schema differences. | Nullable.
- Fallback only on `rate_limit`/`quota` (once). Transient `timeout`/`network`/`invalid_response` get one bounded retry on the same provider. `auth` never falls back. Per-run request budget (3) in config. | SPEC 13.5, no loops. | Retry on everything.
- Gate before AI: only unknown / low-confidence / conflicting fields that are not sensitive, consent, third-party, upload, open-ended, hidden, disabled, populated or custom widgets are candidates. Validator and mapper re-apply the policy after the AI. | SPEC 17.2 risk policy wins. | Trusting the model.
- New sensitive type `government_id` (SSN, passport, Aadhaar, PAN, tax id, driver's licence...). | Found while designing the adversarial AI test: such labels were "unknown" and would have gone to the AI. | Leaving them unknown.
- `MAPPING_FIELDS -> FILLING` was removed; every run goes `MAPPING_FIELDS -> PLANNING -> FILLING`. The Phase 1 state-machine and run-manager expectations were changed explicitly for this. | AI mappings are turned into actions in PLANNING (SPEC 11.8). | Keeping both edges.
- Negative results (model said unknown / proposed a disallowed type) are cached; low-confidence and review-requested ones are not. | Avoid paying twice for the same field; confidence outcomes may change with threshold. | Caching only positives (found by the e2e cache test: sensitive-answer fields were re-requested on every visit).
- E2E mocks HTTP with `context.route` on the two API origins. It does intercept the extension service worker's fetches, so no mock provider exists in any build. A test greps `dist/` to confirm. | Highest fidelity (real provider code runs); brief asked to try route first. | Build-flag mock provider.
- Popup sends `GET_RUN` every 1.5 s while a run is working. | A service worker terminated mid-run is only restarted by an event; the heartbeat wakes it so it rehydrates (found by the kill-mid-AI-call test). If the popup is closed the run resumes on the next wake (popup open, tab event). Documented limitation. | `alarms` permission.
- Custom widgets: inputs with `role=combobox` / `aria-autocomplete` / `aria-haspopup` get `widget: "combobox"` and are left unresolved ("needs a selection"). | Found by the autocomplete portal: typing into an autocomplete was being reported as verified although the page held no selection (SPEC 12.4). Phase 4b implements selection. | Leaving the false success.
- Cross-section duplicates: the same type + label in several sections is filled only in the single clearly personal section (heading matches personal/applicant/contact...), otherwise ambiguous. | "Name" under Previous School must not get the applicant's name. | First occurrence wins.
- Label text "...in this country" matched the `country` alias for a Yes/No select; the select is understood-but-unfillable (no option matches) and never sent to AI. Test label reworded rather than weakening the alias. | The executor refuses non-matching options, so the mis-classification is harmless. | Context-aware alias.

## Phase 5 (job description intelligence)
- Extraction runs in the content script (`src/job/extract.ts`) and is deterministic: JSON-LD JobPosting -> visible h1 / selectors / `<title>` patterns / og tags -> main-content scoring (text length x (1 - link density) + JD-keyword bonus, tightened to the smallest container holding ~all of it). | SPEC 8.1; no AI needed. | Readability-style library (extra dependency, less control over noise rules).
- Visible text only: `hidden`, `aria-hidden`, `display:none`, `visibility:hidden` and the closed part of `<details>` are skipped; buttons, inputs and scripts are never text. | Tabs/accordions requirement; avoids hidden-text injection. | `textContent`.
- Noise exclusion: nav/aside/dialog/forms with inputs, site-level header/footer, ARIA landmark roles, id/class tokens (cookie, consent, sidebar, related, ad-slot...), and any block introduced by a "Similar/Related jobs" style heading. A token whitelist keeps "job-description"/"posting"/"content" containers. | Decoy exclusion. | Hard-coded selectors per site.
- JSON-LD is trusted only if consistent with the visible h1 (token overlap >= 0.5, else the heading wins with a warning); multiple JobPosting blocks pick the one matching the heading; malformed JSON-LD is repaired once (trailing commas/comments) or ignored with a warning; double-encoded HTML descriptions are decoded. | Brief failure case 9; JSON-LD can be stale or wrong.
- Unknown scalars are `null`, lists empty; every guess is recorded in `extractionWarnings` (e.g. "Company inferred from the page title") and lowers `sourceConfidence`. | SPEC 8.2.
- Skills: local dictionary (~150 entries) with synonyms; short caps tokens (ML, NLP, SQL, AWS...) are case-sensitive; ambiguous words (React, Swift, Express, Spring, Go, R...) need capitalisation and/or a skills-list context. Required vs preferred comes from section headings; without headings skills are keywords only (with a warning). | Precision over recall; AI enrichment is the recall path.
- Optional AI enrichment is off by default, behind its own switch, cached by posting hash, and every proposed skill must appear verbatim in the posting. | Cannot invent requirements. | Trusting the model.
- Ranking (`src/job/rank.ts`): documented weights (required 0.35, preferred 0.10, best project 0.20, best experience 0.10, education 0.10, role alignment 0.15), unknown components are dropped and the rest renormalised, every component carries a note, per-project/experience evidence lists "Uses X (required)". Skills count only if the profile records them (skills list, project/experience technologies, or skills named in the user's own descriptions). Education: "Bachelor's or Master's" is satisfied by the lowest listed level or higher. Eligibility language is listed for the user, never scored or answered. | SPEC 8.3 transparency.
- Job context is cached per normalised URL (tracking params and hash dropped) for 6 h in its own storage key; failed extractions are not cached; a cache hit makes no page request. | SPEC 21.1.
- `EXTRACTING_JOB` sits between OBSERVING and DISCOVERING_FORM; the direct edge was removed and the state-machine tests updated. A job on a page with no form is still recorded on the (BLOCKED) run. | The popup must show company/role for job pages that link to a separate form.
- Popup sends `PREVIEW_JOB` on open (read-only; injects the content script under the activeTab grant from the toolbar click). | Real company/role before the user clicks Quick Apply.
- Test infrastructure note: backslashes in shell heredocs / `node -e` snippets were silently halved in this environment, which corrupted regex literals twice (caught by tests/lint). Source edits that contain regexes are now made with the Edit tool. | Process.
